## Planned OAuth scope — requires implementation and integrated validation

- Sign-in is capability-driven, not inferred from a provider name. Exact supported
  providers, host versions and transports remain unconfirmed until integration.
- Supported hosts manage provider tokens; the phone opens an explicit sign-in
  action in an external browser. Do not collect or persist provider access or
  refresh tokens on the phone or embed provider login in a WebView.
- Unknown or unsupported transports must leave sign-in disabled, not attempt
  guessed endpoints or present a successful connection.
- Preserve saved origin/prefix, selected-profile, dashboard authentication and
  client-certificate authority through discovery, sign-in and status readback.
  Do not weaken permission checks to make an account appear connected.
- Test cancellation, failures, expired/unsupported capabilities and stale responses
  on the actual integrated paths before documenting specific supported flows.

## Compatibility and acceptance limits

An Android update does not install or configure Hermes host features or the
optional mobile-push server companion. Existing exact-host mobile-push and
secondary-profile limitations remain unchanged; see
[exact-host compatibility](../mobile-push-exact-host-compatibility.md).
No real-account sign-in, phone upgrade, notification delivery, production signing
or device acceptance is established by this preparation. Debug builds use the
separate `.dev` package and cannot establish production upgrade compatibility.
