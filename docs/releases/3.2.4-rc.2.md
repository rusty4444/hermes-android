# Hermes Android 3.2.4-rc.2

Testing release candidate, base build **3031** (ABI splits `30311` / `30312` /
`30313`). Every split upgrades the highest `3.2.4-rc.1` split (`30303`) in
place. The latest published stable release remains **3.2.3**; this candidate
is a prerelease and is not a stable promotion.

This candidate is independent of `3.2.4-rc.1`, which carried only the
API-versus-Dashboard principal routing test coverage for #253. Everything
below is new on top of that candidate.

## Scheduled jobs are visible before they run (#259)

The **Crons** destination previously listed cron *run* conversations, so a
job scheduled for next week showed nothing until after its first run. Crons
now opens on **Upcoming**, listing scheduled job definitions read from the
cron manager's existing dashboard route, with enabled/disabled state, the
schedule, the next run and the target conversation where the payload supplies
one. **History** keeps the previous run browser, and the full cron manager
still owns every schedule mutation; creating or deleting a job there re-reads
Upcoming on return.

Next-run times always state the zone they are in. The schedule payload
carries numeric UTC offsets rather than a named IANA zone, so a next run is
rendered like `Next: 2026-11-09 09:00 (UTC+11:00)`. Where the payload
supplies no zone information at all, the app says the timezone is unknown
instead of silently assuming the phone's local zone. Named schedule zones,
when present, are shown separately from offset-bearing timestamps; no
conversion is invented.

A connection with no Dashboard route is told that scheduled jobs need one,
which is kept visibly distinct from an empty schedule list.

## Configurable server-side Projects root (#232)

Projects the app created landed under the server's conventional
`<home>/Projects`, while projects created from the TUI or other channels
often live elsewhere, so neither side saw the other's folders.

**More -> Projects folder on the server** now holds a per-saved-connection
root used when the app creates a Project. The default is unchanged, so
existing setups behave exactly as before until the setting is used. When the
dashboard supplies a `locked_root`, that server lock outranks the local
preference and is displayed read-only.

**Projects -> Add an existing folder** enumerates server folders through the
dashboard's existing managed-files route, filters out paths already claimed
by a registered Project, and adopts the chosen folder through the existing
project-creation contract. Where a host does not expose that listing route,
the app says so and falls back to entering a path manually rather than
pretending to have scanned.

Scope limits: changing the root does not move Projects that already exist,
enumeration covers direct non-hidden children rather than recursing,
manually entered paths receive syntactic validation only, and server-side
symlinks are not resolved.

## Clearer API-only send refusals (#253)

On a connection holding only an API-server key, sending into a chat owned by
the Dashboard is refused by the gateway with an in-band `permission_denied`.
The app previously surfaced only the bare refusal.

The terminal failure notice now appends what to check while preserving the
server's own wording verbatim. The wording stays conditional: adding the
connection's Dashboard username and password *may* allow the send, and the
server *may* equally be refusing deliberately. An access-control denial can
be intentional policy, so the note never diagnoses a cause.

Nothing about delivery changed. Send routing, the principal used, the attach
gate and retry behaviour are all untouched, and no prompt is resent.

## Lighter background refresh on the chat list (#149)

The visible-pane refresh ran a full aggregate read every ten seconds,
including the dashboard's `archived=only` paging, even while a filter that
renders no archived rows was selected. The passive refresh is now scoped to
the authority the selected surface actually displays.

Measured as request counts through test fixtures over three refresh ticks:
archive requests on Chats fall from 8 to 2, and on Crons from 10 to 4, in
both cases leaving only the initial scan. The Archived surface keeps its
full-scope refresh unchanged. Selecting Archived fetches the archive
authority immediately rather than waiting for a tick, previously loaded
archived rows and device-local pins and Quick Chat records are preserved
across scoped ticks, and explicit refreshes keep their existing scope.

No device or server transfer volume is measured or claimed; these are
request counts observed through test clients.
