## Planned Usage scope — requires integrated validation

The intended navigation is one **Usage** section covering **Nous, OpenRouter,
OpenAI, Claude and DeepSeek**, not parallel competing usage entry points.

Acceptance requirements for that integration are:

- Distinguish Hermes-recorded activity/model analytics from real provider-account
  quotas. Account quota data must come from the host's `model.options` response;
  recorded tokens or session counts are not account allowance evidence.
- Keep **OpenAI Codex account access separate from paid OpenAI API access**.
  Keep **Claude OAuth account access separate from paid Claude API access**.
  Do not transfer one account mode's quota or availability to the other.
- Present **session and weekly remaining percentages and reset times only where
  the host reports them**. Missing data is unavailable, not zero, unlimited or an
  inferred allowance. **Daily quotas are not exposed** by this planned surface.
- Do not invent token allowances, monetary allowances, balances, pricing or
  subscription entitlements. Do not derive them from recorded usage.
- Preserve the saved dashboard origin/prefix, authentication, selected-profile
  routing and client-certificate boundaries. Do not collect provider credentials
  on the phone or weaken a permission check to make a quota appear available.

Endpoint support and account response shapes remain host-dependent. This local
preparation does not access credentials or real provider accounts. Parent-owned
integration must establish actual supported behaviour and revise these planned
claims before a candidate is offered to testers.

## Existing compatibility limits remain

The prior candidate's exact-host mobile-push limitations are unchanged. At host
`bf0203a794a07aac3ff764972ab9087baa4e4f4e`, launch-profile, explicitly enabled
in-process routing passes authenticated diagnostics, but shared-dashboard
secondary-profile routing lacks a verified identity-forwarding IPC contract and
is rejected. The historical cross-profile host suite remains red; no permission
check was weakened. See [exact-host compatibility](../mobile-push-exact-host-compatibility.md).
A separately launched, explicitly enabled dashboard per profile remains required
for that companion path. RC.2 preparation does not implement shared hosted support.
An APK update does not install or configure Hermes or the optional companion.

**Device acceptance is unavailable.** No real-phone upgrade, notification delivery
or real-account acceptance is established here. Synthetic fixtures, component
passes and local debug builds cannot establish those outcomes. Debug builds use
the separate `.dev` package and cannot prove production in-place upgrades.
