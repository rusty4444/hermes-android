# Hermes Android 3.2.4

Stable release, base build **3032** (ABI splits `30321` / `30322` / `30323`).
Every split upgrades the highest previously distributed split — `3.2.4-rc.2`'s
`30313` — so this installs in place over 3.2.3 or either 3.2.4 candidate. The
production package `com.hermesagent.hermes_android` and signing certificate are
unchanged; install over the existing app rather than uninstalling.

This release covers everything since **3.2.3** and supersedes the `3.2.4-rc.1`
and `3.2.4-rc.2` testing candidates. Its application code is byte-identical to
the tested `3.2.4-rc.2` tree; only release identity and notes differ.

## Scheduled jobs are visible before they run (#259)

The **Crons** destination previously listed cron *run* conversations, so a job
scheduled for next week showed nothing until after its first run. Crons now
opens on **Upcoming**, listing scheduled job definitions read from the cron
manager's existing dashboard route, with enabled/disabled state, the schedule,
the next run and the target conversation where the payload supplies one.
**History** keeps the previous run browser, and the full cron manager still owns
every schedule mutation; creating or deleting a job there re-reads Upcoming on
return.

Next-run times always state the zone they are in. The schedule payload carries
numeric UTC offsets rather than a named IANA zone, so a next run renders like
`Next: 2026-11-09 09:00 (UTC+11:00)`. Where the payload supplies no zone
information, the app says the timezone is unknown instead of assuming the
phone's local zone. Named schedule zones, when present, are shown separately
from offset-bearing timestamps; no conversion is invented.

A connection with no Dashboard route is told that scheduled jobs need one, kept
visibly distinct from an empty schedule list.

## Configurable server-side Projects root (#232)

Projects the app created landed under the server's conventional
`<home>/Projects`, while projects created from the TUI or other channels often
live elsewhere, so neither side saw the other's folders.

**More -> Projects folder on the server** now holds a per-saved-connection root
used when the app creates a Project. The default is unchanged, so existing
setups behave exactly as before until the setting is used. When the dashboard
supplies a `locked_root`, that server lock outranks the local preference and is
displayed read-only.

**Projects -> Add an existing folder** enumerates server folders through the
dashboard's existing managed-files route, filters out paths already claimed by a
registered Project, and adopts the chosen folder through the existing
project-creation contract. Where a host does not expose that listing route, the
app says so and falls back to entering a path manually rather than pretending to
have scanned.

Scope limits: changing the root does not move Projects that already exist,
enumeration covers direct non-hidden children rather than recursing, manually
entered paths receive syntactic validation only, and server-side symlinks are
not resolved.

## Ukrainian and in-app language selection (#255)

Ukrainian joins the shipped locales, alongside a persistent in-app language
selector: choose any generated locale or follow the system default, and the
choice survives restarts and configuration backup restoration.

This change merged **after** the `v3.2.3` tag, so despite appearing in the 3.2.3
changelog entry it is absent from that release's published APKs. **3.2.4 is the
first stable release that actually contains it.** The changelog header carries
the same correction.

Contributed by [@simplaerai-sv](https://github.com/simplaerai-sv), with their
original commits preserved through the merge.

## Clearer API-only send refusals (#253)

On a connection holding only an API-server key, sending into a chat owned by the
Dashboard is refused by the gateway with an in-band `permission_denied`. The app
previously surfaced only the bare refusal.

The terminal failure notice now appends what to check while preserving the
server's own wording verbatim. The wording stays conditional: adding the
connection's Dashboard username and password *may* allow the send, and the
server *may* equally be refusing deliberately. An access-control denial can be
intentional policy, so the note never diagnoses a cause.

Nothing about delivery changed. Send routing, the principal used, the attach
gate and retry behaviour are all untouched, and no prompt is resent.

## Lighter background refresh on the chat list (#149)

The visible-pane refresh ran a full aggregate read every ten seconds, including
the dashboard's `archived=only` paging, even while a filter that renders no
archived rows was selected. The passive refresh is now scoped to the authority
the selected surface actually displays.

Measured as request counts through test fixtures over three refresh ticks:
archive requests on Chats fall from 8 to 2, and on Crons from 10 to 4, in both
cases leaving only the initial scan. The Archived surface keeps its full-scope
refresh. Selecting Archived fetches immediately rather than waiting for a tick,
previously loaded archived rows and device-local pins and Quick Chat records are
preserved across scoped ticks, and explicit refreshes keep their existing scope.

No device or server transfer volume is measured or claimed; these are request
counts observed through test clients.

## Verification

Validated on the integrated tree before this release's identity commit:

- `flutter analyze --no-pub --fatal-infos` — no issues.
- `flutter test --no-pub` — 5,548 visible tests passed, zero failures, zero
  skipped, every started test finished.
- `dart format` — changed Dart files unchanged by the formatter;
  `git diff --check` clean.
- The release identity test, both workflows' embedded identity guards including
  a negative wrong-base case, the README release-window checker and the
  store-notes gate all pass for base 3032.
- The identical application tree was published and verified as `3.2.4-rc.2`:
  downloaded APKs matched package, version name, split codes, ABIs, the
  production signer and the release asset digests, and the repository verifier
  passed with 22 packaged-blob checks per APK.

Not claimed: on-device or emulator acceptance, a live multi-timezone server, a
live multi-root server, or any real gateway authorisation reproduction. The
automated gates above are source and artefact checks, not field testing.
