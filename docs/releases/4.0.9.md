# Ares 4.0.9

Stable patch release `4.0.9+3065`. ABI split codes `30651` (armeabi-v7a),
`30652` (arm64-v8a) and `30653` (x86_64), each above the highest published
4.0.8 split (`30643`). The production package `com.hermesagent.hermes_android`
and signing certificate are unchanged; install over the existing app.

## Fixed

### Sending and live updates on Hermes 0.23.x session-authority gateways (#293, fixes #291)

v4.0.7 fixed `prompt.submit`, but on Hermes 0.23.2 sending still failed with
"Not sent: invalid_params" and opening a chat showed "Live updates are
unavailable: invalid_params". The canonical session authority's params models
are `extra="forbid"`: `session.create` refused the legacy `source: 'desktop'`
(only `cli`/`tui`/`gui`/`acp`/`tool`/`oneshot` are allowed) and `session.resume`
refused the legacy-only `inline_images` key.

The deeper cause was route detection: the app read `session_authority` at the
top level of the `gateway.ready` frame, but the gateway nests it inside
`params.payload`, so the flag was never true on the real wire.

- One wire-shape reader (`WsClient.readyFrameHasSessionAuthority`) now serves
  both the Classic and NextGen gateways.
- `session.create` sends `source: 'gui'` on authority gateways (all five send
  sites covered, including the recovery helpers); `session.resume` omits
  `inline_images`. Legacy gateways keep the exact previous shapes.
- With the flag live, authority gateways also get the intended `reasoning`
  create field and `session.mutate` model switches instead of the legacy
  `reasoning_effort`/`config.set` paths.
- REST history requests keep `inline_images=false`: the canonical stored-reads
  contract accepts it.

Reported by [@shmuelsash](https://github.com/shmuelsash) with a source-level
diagnosis. New regression tests enforce the canonical contract over a loopback
gateway wire and at the NextGen controller level, and reproduce both reported
symptoms on the unfixed code. Known pre-existing limit: the Classic
fire-and-forget pre-bind can race a delayed ready frame once; explicit actions
retry after the frame is pinned and succeed.

### NextGen finds chats on multiplexed gateways (#292)

With the profile left on **Server default**, a multiplexed gateway answered the
profile-less session list from its default store, so NextGen showed "no chats
yet" even when another profile held the chats.

- On save, when no profile was picked and the gateway exposes more than one
  profile, NextGen reads `GET /api/profiles/sessions` (all-profiles counts) and,
  if exactly one non-default profile owns all the chats, saves the connection
  with that profile — updating the same stored row, no duplicate connection.
- Ambiguous, default-only or empty counts keep the server default. Any failure
  keeps the previous behaviour; single-profile and legacy gateways skip the
  extra request entirely.
- An explicit Server-default chip tap is indistinguishable from no selection,
  so auto-select can override a deliberate default choice.
- Testing a connection no longer clears a stored profile when the gateway
  reports an empty profile list.

By [@manuelanguitatrejo](https://github.com/manuelanguitatrejo), with unit tests
for the selection rule, payload parsing and error propagation. Original commits
preserved via a true merge commit.
